## 0.13.10

**Per-drama sequencing, the group step and retained vectors** (owner, 2026-11-21). On top of 0.13.9 (frames files and the local cache), so every group step reads frames from the node's disk.

## 0.13.8

**One ghost-aware reader.** A ghosted blob always has its content (committed, as uncommitted blocks behind an empty commit, or in Nexis's snapshot while it transitions), so no read may fail because of a ghost state, and no file is excluded from ghosting to work around it.

- **The retriever is `RestStore`**, the only store that talks to Azure; `LocalCacheStore`, `StageZipStore`, `RedirectStore`, `SplitStore` and `RecordingStore` forward to it, so every read (whole, ranged, conditional, HEAD/length, download, zip open) goes through it.
- **Identity is content, not ETag.** A blob is the same when its length and `idx_sha256` (when present) match. A ranged read pinned to an ETag that a ghost transition changed (412) is looked at, and read on under the new ETag (remembered, so later reads of the old ETag are not refused); a conditional read treats the same content under a new ETag as unchanged. Only a 404 on the base blob, or different content (Mismatch), is an error.
- **States.** committed: read it. ghost: hydrate (commit the blocks, no data transfer), then read. transitioning: read the snapshot; when the snapshot has gone, wait for the base blob to settle, hydrate and read. An empty or out-of-range answer is settled and asked again (bounded), so a race with Nexis changing state between our read and our look is not an error.
- **HEAD gives the real length** of a ghost or transitioning blob (the recorded `ghostd_size`); nothing is hydrated by a HEAD.
- **Folded in:** `GhostSafeRead` (0.13.4) is now only the pin, `ZipOpen` (0.13.5) hydrates by a plain whole read, the snapshot fallback of 0.13.5 is part of the one sender; `CastCandidates` no longer calls `RestStore` directly.
- **Tests.** `GhostRandomTransitionTests`: a simulated Nexis flips a blob between committed, transitioning (its snapshot disappearing) and ghost at random moments while 8 readers run every kind of read in parallel (about 2 s per seed); every read must return the right bytes. `OneReaderGuardTests`: nothing outside the retriever uses a blob client, the snapshot bookkeeping or ghost hydration.
- **Ghostignore.** The 1,129 per-file `centers.zip` prefixes come out of `.ghostignore.json` on every machine that has them (the file is not in this repository); keep `index/jobs/`, `index/holds/` and `index/gpu-ready/`.
- **Groups build on a real store (live 0.13.7 dry run: 3.9 uploads/min at ~263% CPU of 8 cores, no faster than 0.13.6).** The faster scan and the parallel uploads did not show because the time is in the member-block range reads, which are round trips. Found: `groups build` did start `--threads` uploads at once (default = physical cores), but inside each upload the merged ranges of one centers.zip were read one after the other (the upload's own centers, and each frame chunk's member blocks), so most threads sat waiting on the network. Now the merged ranges of a zip go out together, and the bound is on **requests in flight, not threads: at most 64 ranged reads of centers.zip are in flight in the whole process** (`CentersZip.MaxInFlight`). Adjacent blocks of the same zip were already coalesced into one ranged read (gap up to 32 KB, up to 4 MB per read); that is unchanged.
- **The groups progress line has the breakdown**: `groups: checked N of M (r/min, ETA ...); avg per upload: scan X ms, read Y ms (own centers Z ms), score W ms; R requests, B MB; reads in flight n now, peak p; U uploads at once, T threads each`. A fake store with 20 ms per read (8 uploads, 216 reads) now takes about 0.8 s instead of about 4.3 s serial, peak 56 reads in flight. No real-store measurement from here: please re-run the dry run and compare the `read` figure.
- Member shards are now 0.13.9.

## 0.13.7

Center-scan speedup, and `groups build` now uses the cores (live 0.13.6 dry run: 5.6 uploads/min at ~240% CPU of 8 cores, 4.76 GB peak).

- **Two-stage scan (`scan.mode fast`, default).** Stage 1: the symmetric popcount distance of the query's sign code to every code (8 x XOR + PopCount of a ulong, unsafe pointers, no bounds checks) keeps the best R = max(`scan.rerank` (default 10000), 20 x topC) rows (ties by row; the excluded upload's rows never count). Stage 2: the exact asymmetric LUT score of those R only; the top C come from it in the exact scan's order (score desc, row asc). The old scan is kept as `scan.mode exact` (also env INDEXNODE_SCAN_MODE=exact) to compare live; new config keys `scan.mode`, `scan.rerank`.
- **Batched queries.** The 240 frames of a pre-check / group-check chunk are scanned in ONE pass over the codes in 2048-code blocks (the 128 KB block stays in cache while every query scores it).
- **`groups build` / index job check several uploads at once**, up to `--threads` (default = cores) uploads in parallel, each with its share of the threads for its frames. The checks read the index and the unchanged set; placements are applied after, in index order, so the result does not depend on the thread count. Progress lines count completed uploads.
- Measured on a 4-core CI runner (no 8-core sandbox here, no live store): scan 54-60 ns/(query,center) exact vs 7-8 ns fast single-thread at 280k synthetic centers (about 8x; 6.7 ns in a 240-query batch), 25 ns exact vs 7-9 ns fast wall with the cores busy; at 41k centers 59 vs 25 ns. Top-100 overlap with the exact scan at 280k synthetic centers: 83% at rerank 2000, 93% at 5000, **97.6% at 10000 (the default, owner-approved)**, 99.4% at 20000 (about 16 ns/(query,center) single-thread at 10000 vs 54-60 exact); the best row's cosine was identical for every query at every rerank. Group joins and the mixed flag were identical in both modes.
- Tests: fast scan = exact scan when the shortlist covers the table (order and excluded upload included), same rows at any thread count, best row kept; group joins / mixed cut identical in both modes.

## 0.13.5

Two read paths still failed on Nexis ghosts after 0.13.4.

## 0.9.0

- **Stage batches.** A node takes a batch of dramas (up to `--batch N`, default 6, or about `--batch-hours H`, default 2, of video; best first: priority, then the oldest pending step's idx_added) and runs ONE STAGE AT A TIME across the whole batch: frames, sscd, thumbs, transcribe, ocrsubs, cast, sync (only this node's stages and pending steps). `--lanes N` (default 2) dramas run side by side inside a stage and share that stage's single loaded model; the next stage starts when the current one is done for every drama, and the stage's models are unloaded first, so one stage's models are in memory at a time. Intermediate data stays in a local batch work folder until the batch ends. As each stage finishes for a drama its outputs are uploaded and its step job marked done, so the store always shows each drama's finished stages; a crash resumes every drama from its last finished stage without redoing it. A failed stage is recorded as before, releases only the steps that need it, and the rest of the batch carries on. Downloads, comments, watch and the AI nodes are not part of batches (they run on `--workers`-free independent loops, one job at a time). `--workers`, `--jobs` and `--max-heavy` (and the config keys) are accepted but ignored, with a one-line warning.
- **Hold blobs (`index/holds/<videoId>.json`).** A batch holds a drama with one small blob, not a tag per step. The node creates it (`If-None-Match: *`) if missing, then takes a 60 s blob lease on it; the lease is the hold, renewed about every 40 s with the batch heartbeat. A blob whose lease has expired is taken over by acquiring the lease (atomic, one winner). Metadata `idx_node`, `idx_batch`, `idx_since`, `idx_until` (last renewed, informational) and tags `idx_hold_node`, `idx_hold_until` (search hints) are re-sent on every create and renewal. It is deleted under the lease on a clean stop or when the drama's last batch stage is done, so a dead node loses its holds within a minute and the folder stays tiny. Claimers list `index/holds/` with metadata (a consistent listing) and skip leased dramas; after taking a step's 60 s lease they re-check the job body (`finishedAt` set = already done) and the hold, so a stale tag query can never re-run a finished step. Fixes the Windows BatchTests race (`b:frames` run again). Also fixed: the plain workers now share their retry back-offs, so a job one worker just failed is not retried by the other in the same run (CI: Comments/Network tests).
- **Models are loaded once per process.** Every read-only model (SSCD, OCR detection and recognition, SCRFD/ArcFace/YuNet/SFace face models, CLIP/DINO vision, SenseVoice ASR) is loaded once and used by all workers: `OrtOptions.Shared` returns one ONNX Runtime `InferenceSession` per model file, device and thread count, and `Transcribe.SharedRecognizer` one SenseVoice recogniser. Thread-safety: ONNX Runtime sessions allow concurrent `Run` calls, so ONNX models need no lock and no per-worker session; each call builds its own tensors. The sherpa-onnx recogniser is called with a stream per decode (the session beneath it is the same ONNX Runtime one), also lock-free. The voice-detection (Silero VAD) detector is stateful, so each piece keeps its own small instance. Workers stay independent in everything else. Measured on the real models (SSCD int8, OCR det+rec, SCRFD, ArcFace, SenseVoice, one run each): 0.9 GB for one worker, 1.57 GB for two separate sets, 0.92 GB for two workers sharing.
- `indexnode control` usage lists gpu-hold and --max-per-ip N|off.
- `indexnode --version`.
- `indexnode run` also writes its log to a rolling file: %LOCALAPPDATA%\indexnode\logs\run-<node>.log on Windows, ~/.local/share/indexnode/logs/run-<node>.log on Linux (2 files of up to 20 MB; INDEXNODE_LOG_DIR overrides the folder).
