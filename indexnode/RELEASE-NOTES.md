## 0.13.1

- **Pre-check can no longer be skipped silently on a process claim.** A missing search index or SSCD model, a missing duration, a failed cut or a failed analysis now fails the claim (transient, retried) with the reason, instead of logging "skipped" and going on to frames with no record.
- **The pre-check decision is on the final `done` line** of a process claim (`"pc":"new|partial|canonical"`, read from precheck.json), PASS included; a duplicate still carries it in its trash/why fields.
- **Claim order on a running node is covered by a test**: a `pri` line appended by another process while a claim runs reorders the next claims (priority, then added, then id).
- **The search index builds itself as a queue job** (`search-index`): a follow-up is due 15 minutes after a build when more centers finished while it ran, a catch-up build runs when the head is behind the centers on the store, and each version records `builtAt` (the time it started).
- **Old search-index versions are kept 3 back** (`search.keep-versions`, default 3; 0 keeps only the head); older `index/search/vN/` are deleted after `head.yaml` moves, and a reader that gets a 404 re-reads `head.yaml` once and retries.
- **The catalog (`catalog.json.gz`, one per search-index version) lists every upload the pre-check has seen**, with duration, title, channel, speech language, dubbed, AI score/flag and the pre-check's match (upload, share, offset, cosine). Every entry has four status fields: `state` (processed | metadata-only), `held` ("ai" when held, else null), `checkedBy` (index | precheck) and `data` (full | precheck: sample estimates, no centers in the index). A held upload that is processed later is replaced by its full entry.
- **AI dramas can be held**: the pre-check flags an AI drama and the process claim releases it as held; `indexnode control ai-dramas on|off` (off: held subjects are not claimed, on: they resume at frames) and `indexnode jobs list --held ai` (with the score).
- **The matched upload's duration comes from `download.zip`'s `idx_summary` metadata** (HEAD only, never a hydrate), then the catalog; before, the repacked layout had no `downloaded.json` and every duplicate was "duration unknown: not skipped".
- **Uploads newer than the search index are found by brute force**: the pre-check also compares the sample with the centers of uploads whose centers finished after the index's `builtAt`.
- **A zero-length ranged read no longer sends an invalid range** (`to=-1`): reading an empty range of a blob now returns nothing instead of failing.

## 0.13.0

There is no separate 0.12.0 release: 0.13.0 ships the 0.12.0 pre-check (below) together with the new job queue. Read docs/cutover.md before upgrading a store.

- **Pre-check now runs in the processors.** Downloaders only download and upload; the pre-check (the 0.12.0 analysis and decision rules, unchanged) is the first step of a `process` claim for a drama with no processing done yet, on the stored video (the window is cut with ffmpeg stream copy). Part-processed dramas skip it. A skip changes no upload data: the `done` line carries the decision, the reason and `trash: download.zip/video`, and processing stops. `/v1/precheck` is gone; `/v1/search` and `/v1/health` stay.
- **Pre-check skip marks trash only; cleanup is by hand.** `indexnode trash list` shows the marks, `indexnode trash empty --older-than 30d [--dry-run]` deletes the video blobs and appends `deleted`. No node does it by itself.
- **The job queue is one log.** `index/jobs/` holds an append log in sealed segments, a gzip snapshot (`queue.snapshot.json.gz`, finished subjects slimmed; a plain `queue.snapshot.json` is still read) and per-subject leases (`jobs/active/*`). The snapshot is written only at rollover, and any node may finish a rollover with conditional writes. The old job blobs are never read or written.
- **Control file is `index/jobs/control.json`** (mode, stages, downloads, gpu, message; absent means run). The old `index/control.json` is ignored; leave it at mode=stop.
- **A node refuses to run without the queue**, with one line: run `indexnode jobs migrate --to log` (`--dry-run` first; it refuses while a job or hold is leased and reports what is not carried over: holds, GPU markers, comments jobs). Describe and translate entries are carried only when their inputs are done; the dropped counts are printed as notes. See docs/cutover.md (paths are under `index/jobs/`; `.ghostignore.json` must list `index/jobs/`).
- **`process` is one video per claim**: all the non-AI steps in one go, the models loaded once; the stage batches are gone.
- **Describe and translate only run with `--ai-stages`.**
- **Comments are part of the download** (written with it; a duplicate's metadata entry gets them too); there is no comments stage.
- **Refresh is explicit or dynamic**: explicit schedules as before; dynamic sources use power-of-two tiers with a random hour, and become inactive after a year without a new video.
- **`HeadAsync` never hydrates** a blob.
- **Per-node operation counts** are reported (storage ops per node).

Frames are the parallel axis (the node's threads); member blocks are read once per upload and (upload, center) and cached for the whole pre-check. Below 0.60 -> **new**. **Candidates are uploads, not drama groups:** the store has no cheap group lookup (relations.json exists per upload and is read lazily; there is no group index), so a drama with several copies splits its share across them. ## 0.11.0

- **New step `centers` (after sscd): per-upload k-means "centers", the structure behind screenshot search, dedup and grouping (owner decision 2026-11-19, from PROTOCOL).** Spherical k-means over the upload's stored SSCD vectors (read through the stage-zip store with the frame times): k = min(256, frames), k-means++ seeding (D = 1 - max cosine), 10 iterations, a final assignment, empty centers dropped, seed = first 4 bytes of SHA-256 of the upload id (deterministic, the same bytes with 1 thread or 32). SIMD (`Vector256` fused multiply-add) and the node's thread share. Writes `centers.zip` (stored members): `centers/centers.bin` (columnar, layout in the README) and `centers/manifest.json`. New uploads get a `centers` step job after sscd (it needs `sscd.zip`); the step is due again when sscd.zip changed (centers.zip's `idx_inputs` no longer matches). `process --job <id> --steps centers` works on the repacked store. **Not done yet:** featureless-frame filtering (TODO, every stored row is clustered). Bit codes are not stored per upload.
- **`indexnode centers backfill [--ids <file>] [--since <time|6h|2d>] [--threads N] [--dry] [--limit N]`:** builds centers.zip for every upload with sscd.zip and no current centers.zip (missing, or stale). Meant to run on lancecm5 next to the store.
- **Global search table: `indexnode search-index build [--new-mean] | update`.** Published under `index/search/vN/`: `mean.f32` (the frozen corpus mean, 512 f32 = sum of the uploads' vector sums / total frames), `bits.bin` (one 64-byte sign code of center - mean per center of every upload), `refs.bin` (per row: u32 upload index, u32 center index), `uploads.yaml` (uploads list with the zip's ETag, size and where centers.bin starts, so a query needs no HEAD); `index/search/head.yaml` names the current version and is rewritten with If-Match. **`update` writes a new version with the same mean, files rewritten whole (bits.bin of unchanged uploads is copied from the previous version, only new or changed centers.zip are read);** `build` reads every centers.zip and computes the mean; `build --new-mean` recomputes the mean and every code from the stored center vectors. Two builders racing for one version: the loser fails (files are created only if new).
- **`indexnode search --vector <f32 or f16 file of 512 values> | --image <file> [--top-centers 300] [--top 20]`.** `--image` embeds with the node's own SSCD (static int8 model, `session.x64quantprecision=1`). Query minus the mean, asymmetric bit scan of all centers (float query against the +-1 bits through 8-dimension lookup tables, parallel), top C centers, one HTTP range read per merged run of member blocks (grouped per upload, plain range requests through the REST store), exact cosine on the members; prints upload, time, score and timings (scan / reads / scoring, requests and bytes). The lookup code is `CenterSearch.QueryAsync` (reusable by the download pre-check). The old `search "<text>" --job <id>` (clip) is unchanged.

## 0.10.9

- **Fix: a hung yt-dlp/ffmpeg child can no longer hold a worker forever** (lancecl1, `--write-comments` on mTci9-VD1tM ran about 14 h on 2026-11-18 and about 18 h on 2026-11-19, after storage DNS failures: the lease renewal failed, the engine logged LeaseLost, the child kept running).
- **Wall-clock limit: 5 minutes per yt-dlp / ffmpeg / ffprobe invocation** in the download, comments, refresh and availability stages (all go through `Tools`). On expiry the whole process tree is killed (`Process.Kill(entireProcessTree)`, Windows and Linux) and the job fails as transient with its usual back-off; after the attempt limit (3) it stays failed with "yt-dlp timed out after 5 min". Config `ytdlp.timeoutMinutes` or flag `--child-timeout-minutes N` (0 = no limit).
- **No-output watchdog: 2 minutes.** A child that prints nothing on stdout or stderr for 2 minutes is hung: tree killed, transient failure ("no output for 2 min (hung); killed"). Config `ytdlp.idleMinutes`, flag `--child-idle-minutes N` (0 = off). The download runs with `--newline`, so a live download prints progress lines continuously and never trips it.
- **Lease lost => the job and its child stop.** Renewal now answers within one lease period (a hung call is cut off), and renewals that keep failing for a whole lease period (60 s, the time after which another node may take the job) count as lost: the job's token is cancelled and its child tree killed at once. Failures shorter than that still just retry. An explicit LeaseLost (another node took it) already cancelled the token; the tests now prove the child tree dies with it.
- **The 5 minute default and 480p downloads:** I did not find download timings in the repository or logs available to this session, so I cannot show from numbers that a full 480p download fits in 5 minutes. A very long video on a slow link could exceed it; such a job would retry and then fail with the timeout reason. If the node logs show downloads near that, raise `ytdlp.timeoutMinutes` for download nodes (the idle watchdog still catches real hangs).
- Tests (`ChildLimitsTests`, Windows via powershell/ping, Linux via sh/sleep): wall-clock kill with its grandchild, idle kill, cancel kills the tree, a child timeout fails the job transient and then permanent with the reason, a lost lease kills the child, and hanging or failing renewals count as lost after the lease period.

## 0.10.7

- **Fix: int8 models give the same vectors on every CPU.** `OrtOptions.Make` now sets `session.x64quantprecision=1` on every session (one list, `OrtOptions.ConfigEntries`). Without it ONNX Runtime's u8s8 int8 kernels on x64 CPUs with AVX2 but no VNNI (AMD Zen 3 such as EPYC 7763, lancecm1) saturate their 16-bit intermediate sums, so the int8 SSCD model gave different vectors there than on VNNI/AVX-512 CPUs (measured on 480 stored frames: saturated vs clean median cosine 0.956, p10 0.852, min 0.381; clean int8 vs fp32 median 0.991). The entry only affects quantised ops: fp32 models are unchanged, and it is a plain config entry the CUDA provider ignores (it is set before the CUDA provider is appended; the GPU path is otherwise untouched).
- **Data note: SSCD (and other int8) vectors made by earlier builds on AVX2-without-VNNI CPUs differ from everyone else's** (lancecm1's stored vectors are the saturated result; lancecm5, hexad-host and the hx-8c nodes match the clean one). The affected uploads need their SSCD step redone; that reprocessing is a separate step and not part of this release.
- **Fix: no empty last frames chunk.** A video exactly N x 600 s long got a trailing `frames/NNNN` chunk with 0 frames and a 0-byte `.mjpeg`; thumbs ran ffmpeg on it ("Output file does not contain any stream", exit -22), which was classed Transient and retried forever (it stopped the lancecm5 node twice). The frames step now never writes a chunk with no frames (it is left out of the manifest too). Thumbs, dino and the other chunk readers (`ChunkDir`, the vector reader) skip 0-frame chunks, so existing zips that hold one still work; an ffmpeg "does not contain any stream" failure is now a PermanentFailure, not a retry.

## 0.9.0

- **Stage batches.** A node takes a batch of dramas (up to `--batch N`, default 6, or about `--batch-hours H`, default 2, of video; best first: priority, then the oldest pending step's idx_added) and runs ONE STAGE AT A TIME across the whole batch: frames, sscd, thumbs, transcribe, ocrsubs, cast, sync (only this node's stages and pending steps). `--lanes N` (default 2) dramas run side by side inside a stage and share that stage's single loaded model; the next stage starts when the current one is done for every drama, and the stage's models are unloaded first, so one stage's models are in memory at a time. Intermediate data stays in a local batch work folder until the batch ends. As each stage finishes for a drama its outputs are uploaded and its step job marked done, so the store always shows each drama's finished stages; a crash resumes every drama from its last finished stage without redoing it. A failed stage is recorded as before, releases only the steps that need it, and the rest of the batch carries on. Downloads, comments, watch and the AI nodes are not part of batches (they run on `--workers`-free independent loops, one job at a time). `--workers`, `--jobs` and `--max-heavy` (and the config keys) are accepted but ignored, with a one-line warning.
- **Hold blobs (`index/holds/<videoId>.json`).** A batch holds a drama with one small blob, not a tag per step. The node creates it (`If-None-Match: *`) if missing, then takes a 60 s blob lease on it; the lease is the hold, renewed about every 40 s with the batch heartbeat. A blob whose lease has expired is taken over by acquiring the lease (atomic, one winner). Metadata `idx_node`, `idx_batch`, `idx_since`, `idx_until` (last renewed, informational) and tags `idx_hold_node`, `idx_hold_until` (search hints) are re-sent on every create and renewal. It is deleted under the lease on a clean stop or when the drama's last batch stage is done, so a dead node loses its holds within a minute and the folder stays tiny. Claimers list `index/holds/` with metadata (a consistent listing) and skip leased dramas; after taking a step's 60 s lease they re-check the job body (`finishedAt` set = already done) and the hold, so a stale tag query can never re-run a finished step. Fixes the Windows BatchTests race (`b:frames` run again). Also fixed: the plain workers now share their retry back-offs, so a job one worker just failed is not retried by the other in the same run (CI: Comments/Network tests).
- **Models are loaded once per process.** Every read-only model (SSCD, OCR detection and recognition, SCRFD/ArcFace/YuNet/SFace face models, CLIP/DINO vision, SenseVoice ASR) is loaded once and used by all workers: `OrtOptions.Shared` returns one ONNX Runtime `InferenceSession` per model file, device and thread count, and `Transcribe.SharedRecognizer` one SenseVoice recogniser. Thread-safety: ONNX Runtime sessions allow concurrent `Run` calls, so ONNX models need no lock and no per-worker session; each call builds its own tensors. The sherpa-onnx recogniser is called with a stream per decode (the session beneath it is the same ONNX Runtime one), also lock-free. The voice-detection (Silero VAD) detector is stateful, so each piece keeps its own small instance. Workers stay independent in everything else. Measured on the real models (SSCD int8, OCR det+rec, SCRFD, ArcFace, SenseVoice, one run each): 0.9 GB for one worker, 1.57 GB for two separate sets, 0.92 GB for two workers sharing.
- `indexnode control` usage lists gpu-hold and --max-per-ip N|off.
- `indexnode --version`.
- `indexnode run` also writes its log to a rolling file: %LOCALAPPDATA%\indexnode\logs\run-<node>.log on Windows, ~/.local/share/indexnode/logs/run-<node>.log on Linux (2 files of up to 20 MB; INDEXNODE_LOG_DIR overrides the folder).
